# 验证、性能与审查

## 验证范围

- 局部改动验证受影响入口；公共组件改动抽查代表性使用页面；布局、响应式或交互变化需实际运行并检查关键状态。新增影响、失败、未解决疑点或用户要求时再扩大。
- 修复线上问题时，用能复现故障的代表数据验证；现有测试无法覆盖且有回归风险时补充测试。
- UI 交付前检查改动文件中的重复基础控件、独立基础样式和绕过公共主题的页面覆盖（规则见[组件与设计系统](components.md)）。
- 全站统一覆盖全部目标页面，核对基础控件来源、用法与主题一致；完成约定范围才标记完成，遗留实现列明位置、原因与未完成范围。
- Astryx 页面按项目版本审查指引（`astryx docs is-my-code-good`）验收；Vue 页面依据 shadcn-vue 实际配置与文档核对主题、控件状态和交互。
- 相关工具可用时：sh/bash 用 ShellCheck，PowerShell 用 PSScriptAnalyzer，GitHub Actions 用 actionlint。

## 浏览器

- 真实登录态的线上页面、表单与接口关联排查优先 BrowserSkill（先读其技能）；本地页面与独立测试优先 Playwright CLI。用户指定工具优先；首选不可用时用适合的已连接工具并说明原因。
- 同一页面只由一个工具控制，结束时清理本任务会话。排查聚焦目标区域及相关接口字段；滚动问题在实际容器内验证。

## 性能

- 用户要求优化、出现性能症状，或改动涉及加载、请求、资源与渲染路径时才测量。依据测量或明确症状定位，优先处理影响用户等待的部分。
- 全站优化选代表页面和关键交互记录基线，在相同数据与环境下复测。
- React / Next.js 用 vercel-react-best-practices，按问题读取对应 rules，全面审查才读完整汇编；其他技术栈用项目工具和官方资料。

## 网页审查

- 用户要求体验或视觉评审时用 Impeccable critique，技术质量专项用 audit。可访问性或 Web 实现需补充核对时用 web-design-guidelines，按其流程获取规则，同一次审查复用已获取内容。
